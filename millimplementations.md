# Milling AutoCAM — implementation plan (not built)

Turning and routing both work because they're genuinely 2D problems — a lathe cuts a profile in the XZ plane, a router cuts a profile in the XY plane, and both reduce to "offset this 2D outline by a tool radius and step down." Both are now driven directly off the part's STEP file via `occt-import-js` (`src/lib/cam/stepProfile.js`): turning reads the rotational envelope of every vertex, routing traces the boundary of the flat top/bottom face. Milling is a different class of problem: a real 3D solid with pockets, islands, contoured surfaces, and fixturing constraints, where the toolpath has to reason about the part's actual 3D shape, not a flat cross-section or a single face's outline.

**Update from building turning/routing:** the original version of this doc assumed STEP geometry extraction would need an unproven, heavy WASM CAD kernel integration. That's no longer true here — `occt-import-js` (already a dependency, already used by `CadViewer.svelte` and now `stepProfile.js`) runs fine in Node, and its `brep_faces` output gives clean per-face triangle ranges, not just an undifferentiated mesh. That means the geometry-extraction risk for milling is much lower than originally estimated; the real remaining problem is toolpath *strategy* (how to clear a pocket, how to rough a contoured surface), not getting at the geometry.

**Option A — reuse the routing engine for simple 2.5D cases.** A meaningful subset of FRC mill work is actually 2.5D: a flat profile with pockets and a fixed cut depth per feature, no contoured surfaces. This could reuse `src/lib/cam/routing.js` and `stepProfile.js`'s face-boundary tracing almost as-is — same STEP-derived contour input, same polygon offset, same Z step-down — plus a pocket-clearing strategy (spiral or zig-zag infill between the offset boundary and the pocket floor, rather than just following the boundary) for removing interior material instead of just cutting an edge. Pocket floors would come from the same `brep_faces` classification already used to find the flat face for routing, just applied to interior faces at a lower Z. This is the smallest step from what already exists, and would cover face pockets, slots, and simple 2D profile milling. It would **not** handle contoured (non-planar) surfaces, angled walls, or multi-sided setups.

**Option B — real 3-axis milling on top of the same STEP data.** For arbitrary 3D milling (contoured surfaces, not just planar pockets), the geometry side is now the *validated* part (same `occt-import-js` mesh + `brep_faces` this repo already uses) - what's missing is a real 3-axis toolpath strategy (parallel raster or adaptive clearing over the triangulated surface, gouge/collision checking against the stock). That's a substantially bigger lift than Option A - real 3D CAM toolpath algorithms are their own specialty even when the input geometry is already in hand - and it's still hard to get fully right without a way to run the output against real geometry on real hardware, which this environment doesn't have.

**Option C — the original plan: Fusion 360 Runner.** Point a local Fusion 360 add-in at the part's STEP file and let Fusion's own CAM engine do the actual 3D toolpath generation, reporting G-code back to `cam_jobs` the way `autocam-runner/README.md` documents (that doc's scope is now milling-only). This is still the most capable and lowest-implementation-risk option for genuinely complex 3D milling, since it leans on CAM software that already handles adaptive clearing and collision-checking correctly - the cost is an external process on a machine with Fusion 360, and someone who can test it there.

**Recommendation:** build Option A first - it's a small, low-risk extension of code and geometry-extraction that already exist and are already proven (turning/routing verified against real STEP output). Reach for Option C (Fusion Runner) when a part genuinely needs contoured 3D surfaces Option A can't reach and someone has hands-on Fusion 360 access to validate against; Option B is worth it only if Option C turns out to be impractical, since it duplicates work a real CAM engine already does well.
